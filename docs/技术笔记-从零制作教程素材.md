## 1. persona.js —— 人格解析与注入

### 1.1 文件位置与命名

| 项 | 值 |
|---|---|
| 人格目录 | `D:\wx-bridge\personas\`（`PERSONA_DIR`） |
| 每用户状态目录 | `D:\wx-bridge\data\personas\`（`STATE_DIR`） |
| 文件名 | `<name>.md`，`name` 必须匹配 `/^[a-z0-9][a-z0-9_-]{0,31}$/i`（字母数字开头，最长 32 字符） |
| 遍历规则 | 只收 `.md`；`name` 不过正则直接跳过；单个文件读坏只跳过该文件 |

### 1.2 front-matter 格式

代码用的是**极简自研解析器**（`parseFrontMatter`，`src\persona.js:29`），不引 YAML 依赖：

```js
/^---\r?\n([\s\S]*?)\r?\n---\r?\n?([\s\S]*)$/
// 逐行：/^\s*([A-Za-z_][\w-]*)\s*:\s*(.*)$/
```

能力边界（写教程要明确交代）：

- 只支持**顶层** `key: value`。数组、嵌套对象、多行 `|`/`>` 块、注释 `#` **都不支持**，会被解析成一行字符串或直接忽略。
- 键名规则：字母或 `_` 开头，后接字母数字/下划线/连字符。
- 值：`trim()` 后如果首尾是成对引号（`"` 或 `'`）则去掉一层。
- front-matter 缺失时整个文件都当 body（`meta = {}`）。

### 1.3 实际被读取的字段

| 字段 | 必填 | 缺省 | 用途 |
|---|---|---|---|
| `title` | 否 | 回退成文件名 `name` | 在 `/role` 列表里显示；注入 prompt 时出现在「【角色设定】」后 |
| `description` | 否 | `''` | 只在 `/role` 列表里显示，**不注入 prompt** |
| 正文 body | **是（事实必填）** | — | 整个 body 就是 `persona.prompt`；`body` 为空则 `listPersonas`/`getPersona` 都跳过/返回 `undefined` |

`linmuwan.md` 的 front-matter 只有两个键：

```yaml
---
title: 林慕婉
description: 20岁独立插画师，温柔黏人的避风港。只对你叫宝宝，0说教0指点，只给抱抱。
---
```

其余所有内容（基础档案、性格、硬规则、粘人模式…）都在 body 里，作为 prompt 原文使用。body 里**显式写了「绝对不要写括号里的动作描述」**——这条在代码层还有 `output.stripActions` 兜底（见第 3 节）。

### 1.4 人格切换与按用户绑定

### 1.5 注入到 system prompt 的两种方式

**方式 A：chat 直连模式（实际生产路径）**——`src\chat.js:145 buildChatMessages`：

```js
messages[0] = { role: 'system', content: '你是' + persona.title + '。以下是你的完整人物设定，请严格保持这个角色，不要说"作为一个AI"之类的话。\n\n' + persona.prompt }
```

`messages[1]` 是**动态 system**（每轮都变）：更早对话摘要 + 本轮条数要求 + RAG 片段 + 搜索结果。

分两条 system 的原因（教程里值得单写一段）：早先把「本轮要求」拼在 persona.prompt 末尾，导致 system 前缀每轮都变，DeepSeek 前缀缓存 `prompt_cache_hit_tokens` 恒为 0，3600 token 的人设每条消息全价重付；拆开后 `[0]` 稳定可缓存。

**方式 B：DSH headless 模式**——`src\memory.js:93 buildTask` 把人格文本拼进任务正文最前面；`src\persona.js:151 applyPersona` 是同一套文案的独立封装，顺序固定为 **人设 → 对话历史 → 用户这一轮**，并明确写「完成任务优先于人设表演」（防止人设把「查磁盘占用」答成撒娇）。

## 2. vault.js —— Obsidian 知识库 RAG（BM25 + 中文 bigram）

### 2.1 为什么是 BM25 而不是向量

DeepSeek 没有公开 embedding 接口，本地 embedding 又违背「零依赖」原则。代价是**只匹配字面不匹配语义**（"难受"搜不到"情绪"），所以分数阈值必须当真用：宁可不注入，也不要塞不相关片段。实测语料 109 篇 / 799 KB / 约 645 片段时：建索引 < 1 秒、查询 < 10 ms、内存几百 KB（当前实际库：113 文件 / 1626 片段 / avgLen 101 / 建索引 63 ms）。

### 2.2 索引构建

| 常量 | 值 | 含义 |
|---|---|---|
| `MAX_CHUNK` | 900 | 单片段字符上限 |
| `TARGET_CHUNK` | 700 | 超长段落贪心打包的目标长度 |
| `MIN_CHUNK` | 40 | 低于此长度丢弃（无信息量） |
| `MAX_FILES` | 5000 | 文件数硬上限 |
| walk 深度 | 8 | 目录递归深度上限 |
| 单文件大小 | 0 或 > 2 MB 跳过 | |
| 缓存文件 | `data\vault-index.json` | **只存统计元信息**（vaultPath / files / chunks / avgLen / ms / builtAt），不存索引本身 |

跳过目录 `SKIP_DIRS`：`.obsidian .claude .claudian .git .trash .attachments brain-collector node_modules`，另外**所有以 `.` 开头的名字**都跳过。

切片算法（`chunkBody`）：
1. 按 Markdown 标题行 `/^(#{1,6})\s+(.*)$/` 切段，记录当前小标题 `heading`；
2. 每段 `trim()` 后：`<= 900` 且 `>= 40` 直接成片段；
3. 超过 900 的按空行 `\n{2,}` 拆段，贪心打包到 700（`pack.length + p.length + 2 > 700` 就换包）。

索引结构与懒加载：
- `chunk = { title, heading, text, path, tf: Map, headTf: Map, len }`
- `df`：按**片段**（不是文件）统计 document frequency；`avgLen = totalLen / chunks.length`（0 片段时取 1）
- `ensureIndex(vaultPath)` 懒加载，首次检索才建；同路径复用内存索引；`building` Promise 防并发重复建；`rebuildIndex` 强制重建。

### 2.3 分词（tokenize）

```
1. 全部转小写
2. 英文/数字词：/[a-z0-9][a-z0-9_+#.\-]{1,}/g（长度 >= 2）
3. 中文串 /[\u4e00-\u9fa5]+/g → 全部 bigram（逐 2 字滑窗）
   单字串直接跳过；整串长度 <= 4 时额外把整串也收一份
```

### 2.4 BM25 打分（精确公式）

常量：

```js
K1 = 1.2          // 词频饱和
B  = 0.75         // 长度归一化
HEAD_WEIGHT = 1.8 // 小标题命中加权
```

IDF（`idfOf`，某个词在 0 个片段出现时返回 0）：

```
idf(t) = ln(1 + (N - n(t) + 0.5) / (n(t) + 0.5))
```

正文字段打分：

```
norm = tf * (K1 + 1) / (tf + K1 * (1 - B + B * len / avgLen))
got += idf(t) * norm
```

小标题额外加权（`headTf` 只统计**小标题**，**不含文件名**）：

```
hNorm = htf * (K1 + 1) / (htf + K1)
got += HEAD_WEIGHT * idf(t) * hNorm
```

最终归一化：

```
score = got / idfSum        // idfSum = Σ idf(t)，t 取查询去重后的全部 token
```

两个关键踩坑（教程里可当案例写）：

- **分母只算库里真实存在的词**：IDF 对不存在的词返回 0，所以它们不会抬高分母。早期版本让不存在的词吃最大值 IDF 计入分母，把「我显卡什么型号」打到接近 0，连命中「显卡」的片段都被判不相关。
- **文件名不能进 headTf**：文件名 `游戏.md` 会让整篇所有片段都吃到「游戏」加成，问「喜欢玩什么游戏」时返回游戏项目说明文档，而不是「游戏行为画像」。文件名本身已经在正文词频里算过一次。

### 2.5 查询拆分与合并

`splitClauses`：按 `[，,。！？!?；;、\n]+` 切分，保留长度 `>= 2` 的分句；单分句超过 24 字再按 18 字定长切；最多取 6 个分句。

`searchVault`：
- 待搜查询 = `[整句, ...分句]`，去重，`slice(0, 7)`；
- 每个查询各自打分，结果按 key `path + '|' + heading + '|' + text.slice(0,40)` 取最高分合并；
- 按分数降序 `slice(0, topK)`。
- 参数默认：`topK = 3`，`minScore = 0.35`（config：`ragTopK: 3`、`ragMinScore: 0.35`；自指提问时 `topK` 降为 2）。

### 2.6 注入格式（formatHits）

- 抬头：`【从你自己的笔记里翻到的东西】`
- 每段：`1. 「标题 · 小标题」正文…`，单段裁剪到 `maxCharsPerHit = 420` 字符（超出加 `…`），空白压成单空格
- 尾部三条硬约束：不要照搬原句/不要列成资料摘录；不要说「根据资料」「我看到笔记里写着」；跟当前话题无关就完全不提

### 2.7 画像事实卡（不走 BM25 的第二条路）

触发条件：`isSelfReferential(text)`（`src\index.js:67`）命中 `/关于我|我的(资料|信息|画像|习惯|爱好|电脑|配置|笔记|知识库|数据)|你知道(我|些)|了解我|记得我|我是谁|我是什么|我平时|我玩|我用|我家|你的?(笔记|资料|知识库)|你(写|记)的|库里(有|存)/`。

原因：画像笔记标题写的是「设备/技术栈/数字足迹」，用户问「你知道些关于我的什么信息」，两边几乎没有共同字面词，实测整句只命中 1 条 0.47 的边缘片段。

`digestNote` 抽取规则（纯规则、不调模型、0 token）：

- 单文件 0 或 > 400 KB 跳过；`PROFILE_CACHE` 按 `mtimeMs` 缓存
- 跳过：`#` 开头（标题）、`>` 开头（引用/隐私警告）、` ``` ` 代码围栏、纯分隔符行 `/^[-=|:\s]+$/`、表格表头行（下一行是 `|---|---|` 时）
- 表格行 `| A | B |` → `A：B`（多列用 ` / ` 连接）；`- ` / `* ` 列表项 → 去掉前缀；`key：value` 且整行 <= 120 字 → 原样保留
- Wiki 链接 `[[目标|显示]]` → `目标`
- 单条事实 `< 4` 字丢弃，`> 180` 字截断加 `…`；总预算由 `maxChars` 控制，逐条扣减，超预算 break
- 多篇笔记**按篇平分预算**：`per = max(180, floor(maxChars / relPaths.length))`——不分的话第一篇（用户画像，表格最长）会把预算吃光
- 生产参数：`profileNotes` 三篇（用户画像-自动采集 / 兴趣图谱 / 🧠 第二大脑），`profileMaxChars: 1200`；主动消息里当提问素材时降为 `320`

`formatProfile` 包装成 `【你记住的关于他的资料（来自你自己的笔记，都是真的）】` + 三条要求（自然说出来、挑具体型号数字、不要说「根据资料」/不要一口气念完）。

## 3. output.js —— 输出后处理

### 3.1 实际调用顺序（`src\index.js:468-568`）

```
模型原始文本
 → ① 忙碌标记解析（guessMarker / BUSY，另路）
 → ② extractStickers()      摘出 [sticker:xxx] 标记，正文去残留
 → ③ stripActions()         按 stripActions 模式删括号动作
 → ④ splitIntoBubbles()     拆气泡
 → ⑤ adjustBubbleCount()    强制到本轮目标条数（1-5，且 ≠ 上一轮）
 → ⑥ 表情包决策/频率闸门（含 ensureSticker 兜底）
 → ⑦ ensureEmoji()          仅当本轮不发图时才补颜文字/emoji（三选一）
 → ⑧ sendBubbles()          带打字状态与 2200ms±40% 抖动间隔逐条发
```

顺序不能调换的两个理由：`adjustBubbleCount` 必须在随机合并之前（条数不重复是硬要求，合并只是锦上添花）；表情包必须先定（否则颜文字和表情会同时加，违反「三选一」）。

### 3.2 ① 删括号动作（stripActions）

三种模式（config `stripActions`）：`action`（默认，只删动作）/ `all`（删所有括号内容）/ `keep`（不删）。

`looksLikeAction(inner)` 判定（**宁可漏删，不可误删**）：
1. 空 → 真；
2. 不含任何中文/字母/数字（纯标点符号）→ 真；
3. 命中 `ACTION_HINTS` 词表 → 真。词表覆盖：动作（笑/抱/蹭/摸/拍/捏/靠/贴/牵/搂/叹/摇/点/抬/低/转/皱/眨/看/望/凑/伸/收/退/扑/蹲/站/坐/躺/歪/怔/愣/哼/鼓/腮…）、声音（声/语气/小声/轻声/软声/嘟囔/嘀咕/念叨）、身体部位（眼/脸/手/头/肩膀/背/颈/怀/衣角/脚）、状态（沉默/顿了顿/想了/认真）；
4. 含 `，` 或 `,` 且含中文且长度 `<= 40` → 真（连续动作描写）。

正则要点：
- 全角：`/（([^（）]*)）/g`，回调里判断，命中才删（只处理单层，不处理嵌套）；
- 半角：`/\(([^()]*)\)/g`，**额外要求内含中文**才可能删（英文/代码括号一律保留）；
- `all` 模式：`/（[^（）]*）/g`、`/\([^()]*\)/g`、`/【[^【】]*】/g`、`/\[[^\[\]]*\]/g` 全删。

删后清理（顺序）：多空格 → 单空格；`，\s*，`→`，`；`。\s*。`→`。`；行首孤立标点 `/^\s*[，。、；：]\s*/gm` 删掉；`([。！？…])[ \t]+`→`$1`；3+ 换行 → 2 换行；`trim()`。

**早期教训**：用「长度 ≤6 且无句末标点」兜底，把「（2024年）」「（x+y）」也删了；现在只认明确动作特征。

### 3.3 ② 拆气泡（splitIntoBubbles）

参数（`splitIntoBubbles(text, opts)`）：

| 参数 | 代码默认 | 实际值 | 作用 |
|---|---|---|---|
| `maxMessages` | 3 | 5（`maxBubbles`） | 最多几条 |
| `enabled` | true | true（`bubbleSplit`） | |
| `shortReplyThreshold` | 40 | 0（`shortReplyThreshold`） | 只有「一整段且短于该值」才不拆 |
| `minimumFragmentLength` | 8 | 0（`minimumFragmentLength`） | 低于该长度且无句末标点的碎片会被合并 |

算法：
1. 按空行 `/\n{2,}/` 拆段；
2. 只有 1 段且 `length <= shortReplyThreshold` → 直接返回单条（"好的呀"这种）；
3. 只有 1 段 → 按句末标点 `/(?<=[。！？!?…])/u` 切句；
4. 任一段仍 `> SEGMENT_SOFT_MAX = 60` → 再按句号贪心打包到 60（防「第一条三个字、第二条五十字」的畸形分条）；
5. 合并碎片：碎片定义 = `minimumFragmentLength > 0 && 缺句末标点 && length < minimumFragmentLength`；`last` 或当前段是碎片且合并后 `<= 120` → 合并；
6. 超过 `maxMessages` → 前 `maxMessages-1` 条保留，其余用 `\n\n` 拼进最后一条（**不丢内容**）。

`adjustBubbleCount(bubbles, target)`：
- `want = clamp(round(target), 1, 8)`；
- 多了 → 反复挑**相邻两条长度和最小**的一对，用 `\n` 合并；
- 少了 → 反复挑最长且 `>= 6` 的一条按句切分，从 `ceil(parts.length/2)` 处对半分（guard 最多 10 次）；
- 目标条数由 `pickBubbleCount(last, 1, 5)` 生成：1-5 均匀随机但**排除上一轮条数**（避免节奏机械）。

### 3.4 ③ 长度上限与截断

- 最终气泡未做统一字数裁剪，但在几个入口有硬截断：主动消息单条 `slice(0, 200)`；`/do` 预设输出 `slice(0, 800)`；`/do` 失败信息 `slice(0, 500)`；记忆单条 `MAX_CHARS_PER_MSG = 1200`。
- 单段超长靠 `SEGMENT_SOFT_MAX = 60` 和 `maxMessages` 控制总长度。

### 3.5 ④ 颜文字 / emoji 兜底（ensureEmoji）

参数默认：`kaomojiChance = 0.65`、`emojiChance = 0.35`（config 同名键）。

- 先 `detectMood` 判情绪，**判定顺序有讲究**：`angry → sad → tired → shy(撩人) → shy(害羞) → happy → neutral`。`气死|生气|不爽|讨厌|过分|凶|骂|谁让他|揍|敢|哼|欺负` 排在难过之前（替他出气=愤怒）；`想你|爱你|抱抱|亲亲|贴贴|喜欢你` 必须排在 `happy` 之前，否则「想你了」会被发给开心图。
- 颜文字：整条回复都没检测到时，按 `kaomojiChance` 补一个，挂在**最长气泡**末尾（先 `/[。！？!?…~～\s]+$/` 去尾部标点，再 `' ' + k`）。
- emoji：同理，按 `emojiChance`，随机挂到某个气泡末尾。
- 检测正则：颜文字 `/[\(（][^\)）\n]{0,24}[•´`｡╥﹏ㅂㅁω＼▽◍*・ᴗ◕‿≧∇≦ﾉ٩۶][^\)）\n]{0,24}[\)）]/`；emoji `[\u{1F300}-\u{1FAFF}\u{2600}-\u{27BF}\u{2B00}-\u{2BFF}]`。
- 词库按情绪分组（`KAOMOJI_BY_MOOD` / `EMOJI_BY_MOOD`，happy/shy/sad/tired/neutral 各 2-8 个）。
- 同一个回复**只补一次**：`ensureEmoji` 内部幂等（检测到已有就不再补），且调用点严格受 `if (!stickerNames.length)` 保护。

### 3.6 ⑤ 去重复

- 气泡层面**不去重**（聊天里重复短语是正常的）。
- 去重发生在两个地方：主动消息用 `proactivehistory.isTooSimilar`（见第 5 节）；表情包用 `lastStickerTurn` 轮次冷却 + 类别避让。
- 表情包标记解析（`extractStickers`）容忍：全角冒号 `：`、全角方括号 `［］`、多余空格；正则 `^[ \t]*[[［][ \t]*sticker[ \t]*[：:][ \t]*([^\]]+?)[ \t]*[\]］][ \t]*$`（`gim`）优先整行匹配，其次行内 `[[［]\s*sticker\s*[：:]\s*([^\]]+?)\s*[\]］]`；摘完清理多余空格与空行。

### 3.7 打字延迟（humanDelayMs）

`{ min: 600, max: 2200, perChar: 45, cap: 3500 }`：`base = min(len * 45, 3500)`，叠加 `[min, max)` 抖动，结果再被 `cap` 截断。实际发送用的间隔是 `bubbleGapMs`（实际 2200 ms，±40% 抖动，下限 250 ms）。

## 4. memory.js —— 短期上下文与归档

### 4.1 存储与参数

| 项 | 值 |
|---|---|
| 短期记忆 | `data\memory\<sha1(userId).hex.slice(0,16)>.json` |
| 归档 | `data\archive\chat-YYYY-MM-DD.jsonl`（按 **UTC** 日期分文件：`new Date().toISOString().slice(0,10)`） |
| `MAX_TURNS` | 6（短期只喂最近 6 轮 = 12 条消息） |
| `MAX_CHARS_PER_MSG` | 1200 |
| 生产压缩档位 | `historyRecentTurns: 3` + `historyOlderChars: 40` |

### 4.2 归档 jsonl 格式

每行一条 JSON（append-only，永不覆盖）：

```json
{"at":"2026-10-17T14:28:11.544Z","userId":"<wxid>@im.wechat","question":"在吗","answer":"在呀～"}
```

为什么要归档：`memory\*.json` 只留最近 6 轮，第 7 轮进来就把第 1 轮挤掉，等于「聊天记录」在磁盘上根本没存全。归档给知识库采集器和以后做 RAG 用。归档失败只 `warn`，不影响主流程。

写入顺序（`appendTurn`）：**先归档原文 → 再 push user/assistant → 再 trim 到 `-MAX_TURNS*2` → 落盘**。

### 4.3 历史压缩策略（compressHistory）

- 默认 `recentTurns = 3`、`olderChars = 40`；`keepMsgs = recentTurns * 2 = 6`。
- 超过 `keepMsgs` 时：最近 6 条原文保留；更早的**一问一答并成一行**：`我：<问题前40字>… / 你：<回答前40字>…`，各条 `\s+` 压成单空格。
- 纯文本截断，**不额外调模型**（0 成本）。实测从「6 轮全文 ≈ 700-900 token/条」降到「3 轮全文 + 摘要 ≈ 400-500 token/条」，且有 `MAX_TURNS` 硬上限，聊再久也不膨胀。

### 4.4 加载顺序（buildTask，DSH 模式）

```
1. 人设段（"完成任务优先于人设表演" + 【角色设定】title + prompt）
2. 对话历史（抬头"以下是我与你的最近对话记录，请据此理解上下文："，
   逐条 "我：…" / "你：…"，超过 1200 字截断加 "…（已截断）"）
3. 用户这一轮（"现在我说：" 或首轮的 "我想问你：" + question）
4. 收尾："请直接回答我这句话，不要复述上面的对话记录，也不要用'好的，我来扮演…'这类开场白。"
```

顺序理由：用户这句话必须**紧贴指令**，模型注意力最强；反过来把用户的话放前面，长对话下容易跑偏。

chat 模式下顺序不同：`system[人设] → system[动态上下文+历史摘要] → 最近 N 轮 user/assistant 原文 → user[本轮]`。

### 4.5 其他

- `loadHistory` 有进程内 `Map` 缓存；读失败返回 `[]` 并缓存。
- `clearHistory`：清缓存 + 写 `[]`（`/new`、`/clear` 命令）。

## 5. proactive.js + proactivehistory.js —— 主动消息

### 5.1 协议前提

微信 iLink 的硬限制：发送需要 `context_token`，而它来自用户消息。实测空 token 也能发（服务端会分配 message_id），但没有官方保证。实测**用户最后一次说话之后约 30 分钟内**还能发出去，超过服务端一律 `ret=-2`（prepare failed）。所以「发送窗口」被当成一等的概念处理。

### 5.2 三时间戳（绝对不能混用）

| 字段 | 只由谁更新 | 用来判断什么 |
|---|---|---|
| `lastUserSpokeAt` | 「用户真的说话了」（`touchUser(userId, {userSpoke:true})`） | 静默够不够久、窗口还在不在 |
| `lastProactiveAt` | 「我们成功发出去一条」 | 冷却（`nextDueAt` 的基准之一） |
| `nextDueAt` | 发送成功时 = `now + nextGap()`；`userSpoke` 时若已过期则 = `now`；生成失败时 = `now + max(30_000, nextGap())` | 下一次允许发送的时刻（带随机抖动） |

另有 `silentStreak`（成功发出后 +1，用户说话清零）与 `windowClosed`（发送失败置 true，等用户再说话才重开）。

**踩坑记录**：曾把发送成功也写进 `lastSeenAt`，等于每发一条就把静默计时清零，实际间隔 = `idleBeforeMs + gap`，配 5-10 分钟就变成 10-15 分钟，看起来像「频率怎么调都很低」。

### 5.3 调度周期与参数

调度用**固定短周期轮询**（`setTimeout` 递归，`timer.unref()`），不是「睡完一个 gap 再醒」——gap 是每用户独立随机值，全局长睡眠会丢精度。

| 参数 | 代码默认 | 实际值 | 说明 |
|---|---|---|---|
| `enabled` | false | true | `proactive` |
| `minGapMs` / `maxGapMs` | 60s / 180s | 1min / 3min | `proactiveMinMinutes`/`proactiveMaxMinutes`，每用户独立抽 `[lo, hi)` 均匀，`lo >= 1000ms` |
| `idleBeforeMs` | 60s | 1min | `proactiveIdleMinutes`：用户静默多久后开始搭话 |
| `contextTtlMs` | 30min | 30min | `proactiveContextTtlMinutes`：超过就彻底不再尝试 |
| `tickEveryMs` | 15000 | 15s | `proactiveTickSeconds`，实际 `max(3000, tickEveryMs)` |
| `burstAfter` | 3 | 3 | `proactiveBurstAfter`：连发几次没回应升级 |
| `burstAfterIdleMs` | 5min | 5min | `proactiveBurstAfterIdleMinutes` |
| `burstMinCount`/`burstMaxCount` | 3 / 5 | 3 / 5 | 升级档随机条数 |
| `burstGapMs` | 2500 | **500** | `proactiveBurstGapMs`，±30% 抖动，下限 600 ms |
| 忙碌：`busyGapMs` | 25min | 25min | `busyIntervalMinutes` |
| 忙碌：`busyMinCount`/`busyMaxCount` | 2 / 3 | 2 / 3 | |
| 忙碌：`busyBurstGapMs` | 1500 | 1500 | ±20% 抖动，下限 600 ms |

### 5.4 静默时段（重要澄清）

代码里**没有**按钟点定义的夜间静默时段（没有任何 `hour` 取值判断）。教程里说的「静默时段」实际是**用户静默阈值** `idleBeforeMs`（用户不说话多久后才主动搭话）；若要夜间免打扰，需要自己新增时钟判断——当前没有现成开关。

### 5.5 tick 判定顺序

```
for each user:
  跳过：未初始化 lastUserSpokeAt / userId 含 "test" / windowClosed
  idleMs = now - lastUserSpokeAt
  busy = getBusy(userId)
  ├─ 忙碌模式：base = max(lastUserSpokeAt, lastProactiveAt)
  │    now - base < busyGapMs → skip
  │    wantCount = pick(2,3)；先 keepAlive() 试探续期；compose(busy:true)
  │    发送；成功 bumpSilentStreak + recordProbe{ok:true}；全失败 → closeWindow
  └─ 普通模式：
       idle < idleBeforeMs        → skip（用户还在活跃聊天，别插嘴）
       idle > contextTtlMs        → skip（窗口基本已关，别浪费请求）
       now < nextDueAt            → skip（冷却没到）
       escalateByIdle  = idleMs >= burstAfterIdleMs
       escalateByStreak= silentStreak >= burstAfter
       escalate = 两者 OR
       wantCount = escalate ? pick(3,5) : 1
       compose(...)；为空 → nextDueAt = now + max(30s, nextGap()) 并跳过（避免每 15 秒重试烧 token）
       逐条发：i>0 时等 max(600, burstGapMs + ±30% 抖动)；任一条失败即 break
       成功：lastProactiveAt = now；nextDueAt = now + nextGap()；silentStreak+1
       全失败（sentCount == 0）：closeWindow + warn
```

`recordProbe` 把 `{mode, idleMinutes, sent, total, ok}` 追加到 `data\window-probe.jsonl`，用来反推真实窗口长度。

### 5.6 相似度双档门槛（proactivehistory.js）

`isTooSimilar(text, {limit=12, threshold=0.5})` 判定为重复的四种情况：

1. **完全一致**：去掉标点 `[\s，。！？、,.!?~～…—\-()（）\[\]【】"'""'']` 后 `tn === rn`；
2. **包含**：`tn.includes(rn) || rn.includes(tn)` 且两者较短者长度 `>= 4`；
3. **bigram Jaccard >= threshold**：`bigrams()` = 去掉非中文/字母/数字并转小写后取全部 2 字滑窗集合（集合为空且原串非空时用整串），`jaccard = |A∩B| / |A∪B|`；
4. **万能句式复用**：文本含 `BANNED_PHRASES` 任一句，且最近某条也含同一句。禁用句式 13 条：`在干嘛 干嘛呢 在吗 在不在 吃了吗 吃过了吗 吃没吃 睡了吗 睡了没 在忙吗 忙不忙 你在做什么 在干什么`。

**双档门槛（数值）**：

| 场景 | threshold | 原因 |
|---|---|---|
| 开新话题 | **0.5**（默认，不传即 0.5） | 连「说同一件事」都不许 |
| 接着上一条往下讲（continueMode） | **0.8** | 话题本来就该相同，只拦「几乎一字不差」 |
| 忙碌模式逐条去重 | **0.8** | 忙的时候宁少一条也不重复 |

重试策略（`composeProactive`）：生成后检查 → 重复则重生成一次 → 还重复：continueMode 下**保留当前句**（换无关兜底句才是真「莫名其妙」）；开新话题则改用本地兜底句 `fallbackLine()` 并直接返回。带问题的那一轮还有一道代码检查 `hasQuestion()`（问号 / `吗|呢|呀|吧` 结尾 / `怎么|为什么|为啥|什么|哪[个里儿]|多少|几个|多久|是不是|有没有|要不要|行不行|好不好`），没有就重生成一次。

### 5.7 场景权重与兜底句库

`SCENARIO_HINTS` 权重（总 21）：

| 场景 | weight | 方向 |
|---|---|---|
| `share_seen` | 3 | 分享刚看到的画面（颜色/数量/动作） |
| `share_made` | 3 | 分享今天做出来的东西（含一个小失误） |
| `share_food` | 3 | 分享刚吃到的东西（味道/口感） |
| `share_weather` | 2 | 此刻天气或光线 |
| `share_mood` | 2 | 此刻的小情绪 |
| `report` | 2 | 报备在做什么 |
| `miss` | 2 | 突然想他，不问问题 |
| `cute` | 2 | 撒娇/假装小委屈 |
| `care` | 1 | 轻关心，不追问 |
| `sigh` | 1 | 自言自语式感叹 |

分享类 `share_*` 合计 13/21 ≈ **62%**（用户明确要求「提高分享欲」）。`pickScenario(avoid)`：先排除最近用过的场景，但**至少保留 3 个候选**（否则全被排除会过度收敛），按权重轮盘抽。升级连发固定用 `cute`；忙碌模式用 `BUSY_FLAVORS` 四选一（report / care / wait / cute，均不许提问、不许催）。

本地兜底句库 `FALLBACK`：10 个场景（share_seen/share_made/share_food/share_weather/share_mood/report/miss/care/cute/sigh），每场景 4-5 句，每句必须带**具体细节**（东西、颜色、味道、数量、时间、声音）——「好无聊啊」这种抽象句正是人机感来源。`fallbackLine()` 优先挑最近没用过的场景，场景内乱序逐句过 `isTooSimilar`，全重复则返回 `FALLBACK.sigh[0]`。

发出去之后一律 `rememberLine(text, scenario)` 落盘 `data\proactive-history.json`，结构 `{at, text, scenario}`；文件最多保留 `MAX_KEEP = 40` 条；`recentScenarios` 默认读最近 4 条，prompt 里禁止清单读最近 8 条（continueMode/忙碌只读 6 条且只禁原句）。表情包类别也记在这个文件里（`scenario: "sticker:<类别>"`）。

## 6. searchbudget.js —— 搜索预算

| 项 | 值 |
|---|---|
| 计数文件 | `data\search-budget.json` |
| 每小时上限 | **6**（`searchHourlyLimit`，`0` = 不限制） |
| 每天上限 | **30**（`searchDailyLimit`，`0` = 不限制） |
| 小时键 | `YYYY-MM-DDTHH`（**本地时间**，时分补零） |
| 日期键 | `YYYY-MM-DD`（本地时间） |

文件内容（实测）：

```json
{
  "hourKey": "2026-10-17T22",
  "hourCount": 1,
  "dayKey": "2026-10-17",
  "dayCount": 1
}
```

重置逻辑在 `readState()` 里做「读时惰性重置」：读出旧状态后与当前 `hourKey`/`dayKey` 比对，不一致就把对应计数清零并写回新键。不依赖定时器，重启也不丢。

`canSearch({hourlyLimit, dailyLimit})` → `{allowed, reason, hourUsed, dayUsed, hourlyLimit, dailyLimit}`；先判小时再判天。超预算的行为是**静默降级**：不报错、不提示用户，只写日志 `[搜索] 跳过 —— 本小时已搜 N/6 次，达到上限`，正常聊天继续。

`recordSearch()` 同时 `hourCount += 1`、`dayCount += 1`，**只在真的发出搜索请求时调用**（`src\index.js:315` 在调用 `webSearch` 之前）。

触发条件在 `websearch.needsSearch`（`src\websearch.js:192`）：① 明确说「搜一下/查一下/搜索/百度/谷歌/上网查」；② 问到「我自己的事」→ **返回 false**（该走知识库）；③ 时效性：**时间词必须紧挨询问词**（如 `现在几点|现在多少度|今天.*(几号|天气|新闻)`），不能用 `/现在.*(多少|几|什么)/` 这种跨句正则——早期因此把「你现在都知道些关于我的什么信息」判成需要联网，去搜了一堆「Obsidian 怎么打标签」的教程。

成本依据：一次搜索约 **4000 tokens 输入 + 4.8 秒延迟**，不设闸会十句话搜八次。

## 7. actions.js + shell.js —— /do 预设动作与命令执行

### 7.1 actions.json 字段结构

文件：`data\actions.json`。顶层两个键：`_说明`（字符串数组，防呆注释）与 `actions`（数组）。

单条动作字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | **是**（`loadActions` 过滤条件） | 动作名，用户 `/do 名字` 就这么叫 |
| `command` | string | **是**（同上） | 实际执行的 PowerShell 命令 |
| `aliases` | string[] | 否 | 别名，可多个 |
| `desc` | string | 否 | 一句话说明，`/do` 列表里显示 |
| `danger` | boolean | 否 | 文档语义 = 有风险、执行前确认 |

**`danger` 目前没有被任何代码读取**（全仓只有 `src\actions.js:28` 的说明文字和 `src\actions.js:62` 的默认值）。`/do` 命中预设后是立即执行的，**没有二次确认**。这是当前实现的已知缺口，教程里不要写成「已实现确认」。

### 7.2 匹配优先级（matchAction）

输入 `text` 先 `trim().toLowerCase()`，然后三轮回：

1. `name` **完全相等**；
2. 任一 `alias` **完全相等**；
3. 输入**包含** `name` 或任一 `alias`（子串匹配，所以「帮我开一下记事本」也能命中「记事本」）。

命中即返回，按 actions 数组顺序先到先得。匹配不上 → 回落 DSH（AI 现场处理，几十秒）。

### 7.3 /do 的安全限制（实际生效的三道闸）

1. **用户白名单**（`src\index.js:891-903`）：允许列表 = `cfg.doUsers`（非空时）否则 `cfg.allowedUsers`；两者都空 → 拒绝并回复「⛔ /do 还没启用」，同时把调用者自己的 userId 回给他方便配置；不在列表 → 「⛔ 你没有执行电脑操作的权限」。生产 `doUsers: []`，所以实际由 `allowedUsers` 的单条白名单兜住。
2. **命令白名单**：只能执行 `actions.json` 里预先写死的 `command`，用户输入本身**永不拼进命令**（`matchAction` 只做匹配，不取值）。这是本模块最主要的安全边界。
3. **超时**：
   - `runAction` 默认 `timeoutMs = 20000`（20 秒）；
   - `runShell` 默认 `timeoutMs = 30000`、`cwd = ROOT`；
   - `/do` 回落 DSH 时 `min(cfg.doTimeoutMs || 120000, 180000)`，生产 `doTimeoutMs: 120000`。
   **没有黑名单/正则过滤**——安全性完全来自第 2 条（命令是预置的）与第 1 条（谁能触发）。

输出处理：`r.ok` 时回 `stdout.trim()`，空则回「（已执行，无输出）」（`Start-Process` 这类成功但无输出，不算失败）；失败回 `stderr || error || '退出码 N'`，截断 400 字。

### 7.4 shell.js 执行细节

```js
spawn('powershell', ['-NoProfile','-NonInteractive','-Command', command], {
  cwd, windowsHide: true,
  stdio: ['ignore', outFd, errFd]   // 绑文件描述符，不用管道
})
```

- **不用管道**的原因：受限环境下 Node 创建管道会 `EPERM`，所以 stdout/stderr 各自绑一个临时文件 `data\tmp\cmd-<ts>-<pid>-<rand>.out|.err`，结束后读取再删除。
- `-NoProfile` 避免用户 profile 带来的干扰和延迟。
- 超时：`child.kill('SIGKILL')`，返回 `{ok:false, code:-1, error:'超时 N 秒'}`，同时带已产出的 stdout/stderr。
- 返回 `{ok: code === 0, stdout, stderr, code, ms}`。

## 8. sticker.js + media.js —— 表情包与图片发送

### 8.1 目录结构与命名规则

根目录：`D:\wx-bridge\stickers\`（config `stickerDir` 为空串时用这个）。

两种布局都支持：

| 布局 | 例子 | 生成的 `name` | `label` | `category` |
|---|---|---|---|---|
| 平铺 | `stickers\开心.png` | `开心` | `开心` | `''` |
| 分类 | `stickers\开心\a.jpg` | `开心_1`、`开心_2`…（按文件名 `localeCompare` 排序后编号） | 原始文件名 | `开心` |

- 文件系统里**文件名即标签**，不需要额外配置。

当前实际素材（`stickers\`）：`开心` 15 张、`卖萌搞笑` 2、`平常` 3、`伤心难过` 22、`生气` 22、`喜欢暧昧` 25，合计 **89 张可用**；`_original\` 另存 3 张原图不计入。

### 8.2 选择逻辑（pickSticker）

```
无名字 → 全部里随机一张
精确 name（如 开心_1）→ 命中即用
category 精确（如 开心）→ 该分类内随机一张
name 包含（fuzzy）→ 命中集合里随机一张
都没有 → undefined
```

模型侧用法：人设里写一行 `[sticker:开心]`，由 `output.extractStickers` 摘出。

### 8.3 频率闸门（为什么光靠 prompt 不行）

人设写「每 6~10 条发一次」，模型理解成「别发」——实测 4 个该发的场景 **0/4**；把人格写详细后反弹到 4/6（每条都甩图）。所以代码上闸，参数（生产）：

- `stickerMinTurns: 2`（下限）、`stickerMaxTurns: 3`（上限）、`stickerChance: 0.5`（中间档概率）；
- `gap = 当前回复轮次 - 上次发表情包轮次`：
  - `gap < 2` → 拦掉，哪怕模型自己想发；
  - `gap == 2` → 软闸：模型想发也要先掷骰子（`random < 0.5` 才放行），失败则本轮不发；
  - `gap >= 3` → **强制**补一张（`chance: 1`）。
- 兜底选择 `ensureSticker(bubbles, emitted, {chance, recentCategories, userText})`：模型已给标记则返回 `null`（不干预）；先掷 `chance`；情绪从「用户这句话 + 她的回复」两处一起判（只看她会漏掉「他说他累了」这种场合）；按情绪映射类别池（happy→开心/卖萌搞笑，shy→喜欢暧昧/开心，angry→生气/伤心难过，sad→伤心难过/生气，tired→平常/伤心难过，neutral→平常/卖萌搞笑），最近发过的类别往后排。`stickerChance` 代码默认 0.18（≈ 每 5-6 条一张），生产调到 0.5。
- 位置：插在**倒数第二条之后**（正文说完、还没收尾），只有一条时插在最后，避免一上来就甩图。

### 8.4 图片上传链路（media.js）

三步（与官方 `Tencent/openclaw-weixin` 对齐）：

1. `getuploadurl`：上报 `filekey`（16 字节随机 hex）、`media_type`、`toUserId`、`raw_size`、`raw_md5`、`encrypted_size`、`aes_key`（hex）；返回 `upload_full_url` 或 `upload_param`。
2. **AES-128-ECB + PKCS7** 加密后 POST 到 CDN（`Content-Type: application/octet-stream`）；必须 200，且响应头必须带 `x-encrypted-param`。
3. `sendmessage`，消息项：

```js
{ type: 2, image_item: {
    media: {
      encrypt_query_param: <x-encrypted-param 原样>,
      aes_key: Buffer.from(aesKeyHex).toString('base64'),  // 关键：base64(hex 字符串) = 32 个 ASCII 的 base64
      encrypt_type: 1
    },
    mid_size: <密文字节数>
} }
```

`aesEcbPaddedSize(size) = ceil((size + 1) / 16) * 16`；`mid_size` 必须是**密文**长度不是原文。图片上限 25 MB（`sendImageVariant` 里判）。MIME 按扩展名映射（png/jpg/jpeg/gif/webp/bmp/mp4/mov/pdf/zip/txt），未知走 `application/octet-stream`。

`aes_key` 的编码是最容易搞错的一处：官方写 `Buffer.from(aeskey)`，而 `aeskey` 本身是 hex 字符串，`Buffer.from` 默认按 UTF-8 处理，所以得到的是「32 个 ASCII 字符的 base64」，**不是**「16 字节原始密钥的 base64」。

### 8.5 为什么停用、恢复需要什么

**现状（必须写清楚，否则教程会自相矛盾）**：

- `data\config.json` 里 `allowStickers: true`，自动发送路径（`sendBubbles` → `sendStickerBatch` → `sendImage`）**仍然挂着**。
- 但手动命令被明确关闭（`src\index.js:956-962`），注释原文：

  > 图片/表情包功能已停用：iLink 的图片上传虽然返回成功，但消息在微信客户端始终显示为「已过期」，排查多轮未解决。为免用户发 `/sticker` 后收到错误提示，这里给出明确说明而不是静默失败。

  用户发 `/sticker` 会收到：「图片和表情包功能暂未启用（iLink 图片通道未打通），目前只支持文字和语音。」

- 也就是说：**上传/发送 API 层是通的（拿到 CDN 参数、sendmessage 也返回成功），问题出在服务端/客户端的图片消息契约**，表现为客户端渲染成「已过期」。

**恢复需要做的事**（按可行性排序）：

1. 用真实设备抓一条**手机微信原生发出**的图片消息原始 JSON（`data\received\` 已经会落盘收到的原始消息，可作对照物），逐字段比对 `image_item`：`media.encrypt_query_param` 是否要二次 base64、`aes_key` 到底是 hex 字符串的 base64 还是原始字节的 base64、`mid_size` 用密文还是原文长度、是否需要 `image_item.aeskey` 顶层字段、`encrypt_type` 取值。
2. `media.buildImageItem` 已经预留了排查开关：`opts.topAeskey`（顶层带 `aeskey`）、`opts.encryptType`（传 `null` 去掉 `encrypt_type`）、`opts.doubleB64`（对 `encrypt_query_param` 再 base64 一次），无需改代码即可穷举组合。
3. 打通后把 `/sticker` 分支（`src\index.js:959-962`）的固定回复删掉、恢复原命令实现；并确认 `allowStickers` 与 `stickerChance` 符合预期（当前 0.5 偏高，建议回到 0.18 附近）。
4. 注意当前自动路径是「静默失败」的：`sendStickerBatch` 只 `warn` 日志，客户端侧「已过期」不会抛错，所以线上会持续发出坏图——在修好之前，若要彻底止血，应把 `allowStickers` 置为 `false`。

## 9. actions.json 实例（3 条）

### 示例 1：普通启动类（无 danger）

```json
{
  "name": "打开抖音",
  "aliases": ["开抖音", "抖音"],
  "command": "Start-Process -FilePath 'C:\\Apps\\douyin\\douyin.exe' -WorkingDirectory 'C:\\Apps\\douyin'",
  "desc": "启动抖音客户端"
}
```

要点：`Start-Process` 成功时无 stdout，`runAction` 会回「（已执行，无输出）」；必须带 `-WorkingDirectory`，否则部分客户端会在错误目录启动。

### 示例 2：带 fallback 的启动 + 输出型查询

```json
{
  "name": "打开浏览器",
  "aliases": ["开浏览器", "浏览器"],
  "command": "Start-Process msedge.exe -ErrorAction SilentlyContinue; if (-not $?) { Start-Process 'C:\\Program Files (x86)\\Microsoft\\Edge\\Application\\msedge.exe' }",
  "desc": "打开 Edge 浏览器"
}
```

```json
{
  "name": "查磁盘空间",
  "aliases": ["看空间", "剩余空间", "磁盘空间", "C盘空间"],
  "command": "Get-PSDrive C,D,E,F -ErrorAction SilentlyContinue | Select-Object Name,@{n='已用GB';e={[math]::Round($_.Used/1GB,1)}},@{n='剩余GB';e={[math]::Round($_.Free/1GB,1)}} | Format-Table -AutoSize | Out-String",
  "desc": "列出各磁盘的已用和剩余空间"
}
```

要点：输出型命令必须 `| Out-String` 才能把格式化表格变成字符串（否则 stdout 为空）；`@{n='';e={}}` 计算属性用来把字节换成 GB；`-ErrorAction SilentlyContinue` 防止不存在的盘符报错中止整条命令。

### 示例 3：带 `danger` 标记（注意：标记本身不生效）

```json
{
  "name": "锁屏",
  "aliases": ["锁电脑"],
  "command": "rundll32.exe user32.dll,LockWorkStation",
  "desc": "锁定电脑屏幕",
  "danger": true
}
```

要点：`danger: true` 只是**约定/文档**，代码不会弹确认，`/do 锁屏` 会立即执行。要真正做确认，需要在 `matchAction` 命中后加一道「先回确认句 + 记录 pendingStatus + 下一条消息匹配 `确认/取消`」的状态机（当前没有）。
