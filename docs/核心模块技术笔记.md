# wx-bridge 核心模块技术笔记（ilink / chat / websearch / dsh / launch）

> 代码基线：`D:\wx-bridge`，Node ESM（`"type": "module"`），零外部依赖，`engines.node >= 18`。
> 本文所有端点、字段、常量均取自源码，行号对应 `wx-bridge/src/*.js` 与 `wx-bridge/launch.js`。

---

## 0. 总体链路

```
手机微信 ⇄ 微信 iLink Bot 服务器 (https://ilinkai.weixin.qq.com)
                ↑ 长轮询 getupdates
           wx-bridge 进程 (src/index.js，launch.js 起停)
                ├─ chat 模式 → https://api.deepseek.com/chat/completions
                ├─ dsh 模式  → spawn node bin.js --profile headless "<task>"
                └─ 可选联网 → https://api.deepseek.com/anthropic/v1/messages + web_search 工具
                ↓ sendmessage / sendtyping
           回到手机微信
```

两个模式共用同一条业务链路（人设、记忆、拆条、指令），只在"真正调模型"那一步分叉（`src/index.js:404-429`）。`--mode` 默认值是 `dsh`（`src/index.js:86`），而 `launch.js` 的默认值是 `chat`（`launch.js:100`）。

## 1. iLink 协议层（src/ilink.js，共 466 行）

### 1.1 机器人从哪来

iLink Bot 是**微信官方的 Bot API**（不是 hook 个人号）。本项目早期参考 `wechaty-puppet-claw-wechat` 的逆向实现，现在端点、字段、版本编码**以腾讯官方实现为准**：仓库 `https://github.com/Tencent/openclaw-weixin`、包 `@tencent-weixin/openclaw-weixin@2.4.10`（MIT）——见 `src/ilink.js:1-15`。

- **bot id / token 不是去哪个后台申请来的**，而是扫码登录后由服务端下发：`ilink_bot_id`（形如 `<bot_id>@im.bot`，即 `accountId`）与 `bot_token`（形如 `xxxx@im.bot:0600003e...`）。所以"获取 bot"= 跑一次二维码登录流程。
- App 标识：`ILINK_APP_ID = 'bot'`（`src/ilink.js:30`）。官方从 package.json 的 `ilink_appid` 字段读，并且**每个请求都带 `iLink-App-Id` 头**；缺了它文字消息还能过，但媒体通道可能不认。
- 通道版本 `CHANNEL_VERSION = '2.4.10'`，同时用于 `base_info.channel_version` 和 `iLink-App-ClientVersion` 头，二者必须自洽。换算公式：`major<<16 | minor<<8 | patch`，2.4.10 → `132106`（`buildClientVersion()`，`src/ilink.js:48-56`）。
- 三条硬约束（官方明确）：① 所有 `sendmessage` 必须带 `context_token`，它只能来自用户消息 → **bot 不能主动发起会话**；② 只支持 1:1 私聊（收到的消息里 `group_id` 恒为空串）；③ `errcode -14` = 会话过期，需重新扫码（`isSessionExpired()`，`src/ilink.js:151-153`）。

### 1.2 端点清单

基址 `ILINK_BASE_URL = 'https://ilinkai.weixin.qq.com'`（`src/ilink.js:18`），CDN 基址 `CDN_BASE_URL = 'https://novac2c.cdn.weixin.qq.com/c2c'`（`src/ilink.js:19`）。除两个 GET 外全部是 `POST + JSON`。

| 用途 | 方法 | 路径 | 关键参数 |
|---|---|---|---|
| 取登录二维码 | GET | `/ilink/bot/get_bot_qrcode?bot_type=3` | `bot_type=3`（ClawBot 类型） |
| 轮询扫码状态 | GET | `/ilink/bot/get_qrcode_status?qrcode=<code>` | 只带 `iLink-App-ClientVersion` 头，无 token |
| 上线通知 | POST | `ilink/bot/msg/notifystart` | `{}` |
| 下线通知 | POST | `ilink/bot/msg/notifystop` | `{}` |
| 长轮询收消息 | POST | `ilink/bot/getupdates` | `{get_updates_buf, sync_buf: ''}` |
| 发消息 | POST | `ilink/bot/sendmessage` | `{msg:{...}}` |
| 取输入凭证 | POST | `ilink/bot/getconfig` | `{ilink_user_id, context_token}` |
| 发"正在输入" | POST | `ilink/bot/sendtyping` | `{ilink_user_id, typing_ticket, status}` |
| 申请 CDN 上传地址 | POST | `ilink/bot/getuploadurl` | 见 1.6 |
| CDN 上传 | POST | `https://novac2c.cdn.weixin.qq.com/c2c/upload?encrypted_query_param=…&filekey=…` | 密文二进制 |
| CDN 下载 | GET | `https://novac2c.cdn.weixin.qq.com/c2c/download?encrypted_query_param=…` | 当前未使用 |

### 1.3 请求头与 base_info

`buildHeaders(token)`（`src/ilink.js:161-172`）：

| 头 | 值 |
|---|---|
| `Content-Type` | `application/json` |
| `AuthorizationType` | `ilink_bot_token`（固定） |
| `X-WECHAT-UIN` | 微信客户端要求的伪随机值：随机 uint32 大端 → 十进制字符串 → base64（`randomWechatUin()`，每次请求重新生成） |
| `iLink-App-Id` | `bot` |
| `iLink-App-ClientVersion` | `132106`（十进制字符串） |
| `Authorization` | `Bearer <bot_token>`（仅在需要鉴权的请求上） |

每个 POST 的 body 都会被 `postJson` 统一附加元信息（`src/ilink.js:175-180, 196`）：

```json
{"...业务字段": "...", "base_info": {"channel_version": "2.4.10", "bot_agent": "WxBridge/1.0.0"}}
```

`bot_agent` 是 UA 风格的自我标识（`product *( SP product )`，`name/version [(comment)]`），只做服务端日志归因，不参与鉴权；由 `sanitizeBotAgent()` 逐 product 清洗（字段截断 name/version 32 字节、comment 64 字节，总长 ≤ 256 字节，超长从尾部整 product 丢弃），非法则回退 `WxBridge`。启动时 `index.js` 调 `setBotAgent(cfg.botAgent)` 注入（`src/index.js:1052`）。

### 1.4 二维码登录完整流程（src/index.js:129-189）

1. `GET /ilink/bot/get_bot_qrcode?bot_type=3` → 返回 `{qrcode, qrcode_img_content, ...}`。
   - 校验：两者任一为空就抛 `接口没有返回二维码`。
2. **二维码不用图片，而是把 `qrcode_img_content`（一条链接）直接打到控制台**，移动端微信打开该链接即可完成登录（`src/index.js:143`）。
3. 轮询：每 **2000 ms** 一次 `GET /ilink/bot/get_qrcode_status?qrcode=<qrcode>`，单张二维码等待窗口 **150_000 ms（约 2 分钟，与提示文案一致）**。
4. `status.status` 取值 `wait / scaned / confirmed / expired`，状态变化时才打印（"已扫码，请在微信里点「确认登录」"→"登录确认成功"→"二维码已过期"）。
5. `confirmed` 时校验 `bot_token`、`ilink_bot_id`、`ilink_user_id` 三字段齐全，然后落盘：

```json
// data/credentials.json（保存 mode 0o600，写入时追加 savedAt）
{
  "token": "<bot_token>",
  "baseUrl": "https://ilinkai.weixin.qq.com",
  "accountId": "<bot_id>@im.bot",
  "userId": "<wxid>@im.wechat",
  "savedAt": "2026-10-17T07:18:13.761Z"
}
```

   即：`token=bot_token`、`accountId=ilink_bot_id`、`userId=ilink_user_id`、`baseUrl=status.baseurl ?? 请求时基址`（服务端可换基址）。
6. 二维码过期则**重新取码，最多 8 轮**（round 1..8），8 次全过期抛 `连续 8 次二维码过期`。
7. 复用逻辑：启动时 `loadCred()` 读 `data/credentials.json` 并做字段校验（token/baseUrl/accountId/userId 都是非空字符串），失败才走登录；`--login` 强制重登，`--logout` 删除凭证（`src/index.js:969-973, 1047-1049`）。
8. 运行期遇到 `-14`：删除凭证 → 重新走完整登录 → 清空 `contextTokens`、`cursor = ''` → 继续轮询（`src/index.js:1603-1617`）。

### 1.5 长轮询 / 游标 / 重试

- 请求体：`{get_updates_buf: cursor, sync_buf: ''}`（`src/ilink.js:268-278`）。**游标只存在内存**（`let cursor = ''`，`src/index.js:1056`），进程重启后从空串开始。
- 响应：`{get_updates_buf, longpolling_timeout_ms, msgs: [...]}`。
  - 有新 `get_updates_buf` 就替换 cursor（`src/index.js:1509`）。
  - 服务端可以建议下一轮时长：`pollTimeoutMs = clamp(longpolling_timeout_ms, 5000, 120000)`；初始 **40000 ms**（`src/index.js:1057-1058, 1512-1514`）。
- 单次请求超时同时受 `AbortSignal.timeout(timeoutMs)` 和外部 `signal` 约束（`AbortSignal.any`，`src/ilink.js:190-191`）。
- 空轮询不报错，每 20 次打印一次"仍在等待…"（`src/index.js:1517-1522`）。
- 出错重试：指数退避，起点 **1000 ms**，每次 × 2，上限 **30000 ms**，成功一轮立即重置为 1000（`src/index.js:1596, 1620-1621`）。`AbortError/TimeoutError` 不计入退避，直接下一轮。
- 过滤与落盘：只处理 `message_type === USER(1)` 且 `from_user_id` 非空的消息；`--mode=dsh` 或 `--verbose` 时把原始消息 JSON 落到 `data/received/<ISO时间>.json`（调试协议差异的"权威对照物"）。
- `context_token` 按 `from_user_id` 存进 `Map`（`state.contextTokens`），发送时回用；**没有 token 就根本发不出去**。

### 1.6 发文本 / 发图片 / 正在输入

**发文本**（`sendMessage()`，`src/ilink.js:284-302`）：

```json
POST ilink/bot/sendmessage
{
  "msg": {
    "from_user_id": "",
    "to_user_id": "xxxxx...@im.wechat",
    "client_id": "<randomUUID()>",
    "message_type": 2,
    "message_state": 2,
    "context_token": "<用户消息里带回的 token>",
    "item_list": [{"type": 1, "text_item": {"text": "你好"}}]
  }
}
```

`message_type: 2` = BOT；`message_state: 2` = FINISH（枚举 `MSG_TYPE{0 NONE,1 USER,2 BOT}`、`MSG_STATE{0 NEW,1 GENERATING,2 FINISH}`、`ITEM_TYPE{0 NONE,1 TEXT,2 IMAGE,3 VOICE,4 FILE,5 VIDEO,11 TOOL_CALL_START,12 TOOL_CALL_RESULT}`）。
应用层发送前用 `splitText(text, 2000)` 按 **2000 字**分块，优先在换行处切（切点 < limit*0.5 时硬切）（`src/ilink.js:452-464`）。

**正在输入**（两步，`src/ilink.js:321-339`）：
1. `POST ilink/bot/getconfig` `{ilink_user_id, context_token}` → 拿 `typing_ticket`；
2. `POST ilink/bot/sendtyping` `{ilink_user_id, typing_ticket, status}`，`TYPING_STATUS{ TYPING:1, CANCEL:2 }`。

外层 `tryTyping()` 是"尽力而为"：`cfg.sendTyping` 关闭、无 context_token、无 ticket、任何异常都静默跳过（`src/index.js:214-227`）。

**发图片**（三步，`src/ilink.js:344-398` + `src/media.js`）：
1. `POST ilink/bot/getuploadurl`：`{filekey(16 字节 hex), media_type(IMAGE=1/VIDEO=2/FILE=3/VOICE=4), to_user_id, rawsize, rawfilemd5, filesize(=PKCS7 补齐后密文长度), no_need_thumb:true, aeskey(hex)}` → 返回 `upload_full_url` 或 `upload_param`（二选一）。
2. 文件用 **AES-128-ECB**（Node 默认 PKCS7）加密，`POST` 到 CDN（`Content-Type: application/octet-stream`），必须 **HTTP 200**；从响应头 `x-encrypted-param` 取 `encryptQueryParam`，失败看 `x-error-message`。
3. `sendmessage` 带 `item_list: [{type: 2, image_item: {media: {encrypt_query_param, aes_key, encrypt_type: 1}, mid_size: 密文字节数}}]`。

⚠ `aes_key` 编码坑（写教程必须强调）：官方是 `Buffer.from(aeskeyHex).toString('base64')`，即把 **32 个 ASCII 字符的 hex 字符串**做 base64（44 字符）；写成 `Buffer.from(hex,'hex')` 得到 16 字节密钥的 base64（24 字符）→ 对端解不出、图片显示"已清理/已过期"。当前项目**图片通道仍未打通**（`src/index.js:956-962` 明确停用 `/sticker`），单图上限 **25 MB**。

### 1.7 消息体结构（收）

实测样本（`data/received/2026-10-17T11-08-46-269Z.json`）：

```json
{
  "seq": 26,
  "message_id": 7517179794432555000,
  "from_user_id": "<wxid>@im.wechat",
  "to_user_id": "<bot_id>@im.bot",
  "client_id": "mmassistant_bypmsg_inbox_...",
  "create_time_ms": 1792235325358,
  "update_time_ms": 1792235325485,
  "session_id": "",
  "group_id": "",
  "message_type": 1,
  "message_state": 2,
  "context_token": "AARzJWAFAAAB...",
  "root_id": 0,
  "parent_id": 0,
  "item_list": [{
    "type": 1, "msg_id": "v1:3260665301780327917", "is_completed": true,
    "at_bot_username_list": [], "button_item_list": [],
    "text_item": {"text": "你在干嘛"}
  }]
}
```

- **发件人** = `from_user_id`（形如 `<id>@im.wechat`）；bot 自己 = `to_user_id`（`@im.bot`）。
- **群聊标识** = `group_id` / `session_id`，iLink 只支持 1:1，两者恒为空串；item 上另有 `at_bot_username_list`（群 @ 信息，单聊为空）。
- **消息类型** = `message_type`（1 用户 / 2 bot）+ item 级 `item_list[].type`。
- 文本提取 `extractText()`：`type==1` 取 `text_item.text`，`type==3`（语音）取 `voice_item.text`（微信自带语音转文字，所以纯文本桥也能吃语音输入），多段用 `\n` 拼接（`src/ilink.js:420-433`）。

### 1.8 错误模型

`ApiError{message,status,code}`（`src/ilink.js:141-148`）：HTTP 非 2xx，或 body 里 `ret!==0` / `errcode!==0`，都抛错，`code` 取 `ret` 或 `errcode`（`-14` 即会话过期）。

## 2. chat.js —— 直连 Chat API（187 行）

### 2.1 为什么要它

DSH headless 是编码 agent，每请求都带系统提示词 + 19 个工具定义（**约 7000–17000 tokens**），纯聊天全用不上。本模块只发"人设 + 历史 + 本轮"，输入降到**约 2400 tokens**（`src/chat.js:1-10`）。

### 2.2 请求

- **端点**：`baseUrl + '/chat/completions'`，默认 `baseUrl = 'https://api.deepseek.com'` → `https://api.deepseek.com/chat/completions`。**标准 OpenAI 兼容**，不是 Anthropic 兼容端点（Anthropic 端点只用在 websearch.js）。
- **默认模型**：`deepseek-v4-flash`（`src/chat.js:50`；运行期取 `cfg.chatModel`，`src/config.js:31`）。
- **默认温度**：`1.3`（`src/chat.js:52`；运行期 `cfg.chatTemperature`）。
- **默认超时**：`60_000 ms`（`src/chat.js:53`；运行期传 `cfg.taskTimeoutMs = 180_000`）。
- **请求头**：`Content-Type: application/json`、`Authorization: Bearer <key>`。
- **请求体**：只有 4 个字段——`{model, messages, temperature, stream: false}`。**没有 `max_tokens`，没有 `system` 顶层字段**（系统提示是 messages 里的 `role:"system"`）。

响应：`choices[0].message.content`（正文）与 `choices[0].message.reasoning_content`（推理，可选），`usage` 原样返回。返回对象：

```
{ok, text, reasoning?, usage?, ms, code?, error?}
```

### 2.3 失败处理（重要，别写成有重试）

- **没有重试**：一次失败即 `{ok:false, code, error}` 返回，重试只在**外层长轮询**和**表情包选图的二次生成**（`src/index.js:1368`）里存在。
- 失败分支：无 key（`code:-1`，提示检查 `~/.dsh/.credentials.yaml` 的 `DEEPSEEK_API_KEY`）；HTTP 非 2xx 或非 JSON（`code = res.status`）；正文为空（`code:0`，`模型没有返回内容`）；`AbortError` → `超时 N 秒未响应`（`code:-1`）。
- 计时：`started = Date.now()`，每条结果都带 `ms`。

### 2.4 token 估算

**代码里没有 token 计数器**，只有三类经验值 + 一个"按字符"的历史压缩策略：

- 常量注释：输入 ~2400 tokens（chat 模式）vs ~17000 tokens（DSH headless）vs 一次搜索 ~4000 tokens；`profileMaxChars: 1200` ≈ 780 tokens。
- 历史压缩 `compressHistory` 按 `recentTurns=3` 轮全文 + 更早每轮 `olderChars=40` 字摘要（`src/config.js:124-127`，实际压缩在 `memory.js`）。
- 真实用量靠响应里的 `usage`（含 `prompt_cache_hit_tokens` 之类的字段，代码只是透传，不解析）。

### 2.5 messages 组装（省 token 的关键，src/chat.js:145-187）

顺序固定，直接决定能不能吃上前缀缓存：

```
[0] system  人设          ← 固定不变，DeepSeek 前缀缓存可命中
[1] system  本轮动态上下文 ← 每轮都变（条数要求 / 知识库片段 / 搜索结果 / 更早对话摘要）
[2..] user/assistant      ← 最近 recentTurns 轮原文
[n] user    本轮这句话
```

把"本轮要求/搜索结果"从人设里拆出来的原因（源码注释实测）：以前拼进 system[0]，整个前缀每轮都变 → `prompt_cache_hit_tokens` 恒为 0，3600 token 的人设每条消息全价重付；拆开后只付一半。

### 2.6 读 key 逻辑（`readApiKey()`，src/chat.js:16-32；dsh.js / websearch.js 各有一份同构实现）

1. `process.env.DEEPSEEK_API_KEY` → `{key, source:'environment'}`（最高优先级）。
2. 依次尝试 `~/.dsh/.credentials.yaml`、`~/.dsh/credentials.yaml`，正则 `^\s*DEEPSEEK_API_KEY\s*:\s*["']?([^"'\s#]+)["']?\s*$`（m 多行）。
3. 都没有 → `{key:'', source:'none'}`，调用方给中文报错。

注意：`index.js` 启动时**读一次**存进 `API_KEY` 常量（`src/index.js:89`），配置写入路径明确 `delete next.apiKey`——密钥永不落进 `config.json`（`src/config.js:379`）。

## 3. websearch.js —— DeepSeek 原生联网搜索（213 行）

### 3.1 调用方式

复用 DSH 自带的 `@deepseek-ai/dsh-web-search-deepseek` 协议，**同一把 `DEEPSEEK_API_KEY`**，不需要另申请搜索服务。代价：DeepSeek 没有独立搜索端点，一次搜索 = 一个完整模型轮次，所以更贵更慢（`src/websearch.js:1-11`）。

- 端点：`baseUrl + '/messages'`，默认 `https://api.deepseek.com/anthropic/v1` → `https://api.deepseek.com/anthropic/v1/messages`（**Anthropic Messages 兼容**）。
- 请求头：`x-api-key` 与 `authorization: Bearer <key>` **同时发**、`anthropic-version: 2023-06-01`、`content-type: application/json`、`accept: application/json`、`user-agent: wx-bridge/1.0.0`。
- 请求体：

```json
{
  "model": "deepseek-v4-flash",
  "max_tokens": 2048,
  "messages": [{"role":"user","content":[{"type":"text","text":"Perform a web search for the query: <query>"}]}],
  "tools": [{"type":"web_search_20250305","name":"web_search","max_uses":3}]
}
```

- 超时：模块默认 **90_000 ms**；`index.js` 调用时传 `cfg.searchTimeoutMs = 60000`。
- 解析 `mapResponse()`：从 `content[]` 里取 `type==='web_search_tool_result'` 块的 `content[]` 中 `type==='web_search_result'` 项，去重得到 `{url, title, snippet, publishedAt(page_age)}`；`snippet` 来自同响应的 `text` 块 `citations[].cited_text`；`answer` 是模型在 tool-use 循环里读完网页后写的摘要（2026-10-18 起**必须注入**回答提示词，见 3.3）。**没有结果块 → `ok:false`（可能没触发搜索）**。

### 3.2 触发条件

两道闸（`src/index.js:305-336`）：

1. `cfg.autoSearch === true`（默认 true）且 `needsSearch(text)` 命中；
2. 通过搜索预算 `canSearch({hourlyLimit: 6, dailyLimit: 30})`（`src/config.js:113-116`，超预算**静默跳过**并打日志）。

`needsSearch()` 规则顺序（`src/websearch.js`，2026-10-18 修正）：
① 明确要求搜：`搜一下|搜搜|查一下|帮我查|查询|搜索|百度|谷歌|上网查` → true；
② 自指问题（`关于我|我的(资料|信息|画像|...)|你知道我|了解我|记得我|我是谁`）→ **false**（交给知识库，别联网）；
③ 时效性：
- `现在几点|现在多少度|现在什么天气|现在的?(价格|汇率|股价)`
- `(今天|今日|昨天|明天|今儿|这两天)[^。！？!?]{0,14}(天气|气温|温度|几号|星期几|多少度|新闻|发生|下雨|下雪|降温|冷不冷|热不热)`
- `(天气|气温|温度)[^。！？!?]{0,8}(什么样|怎么样|如何|多少|咋样|好不好|冷不冷|热不热)`
- `最新.{0,6}(消息|进展|版本|新闻|动态|价格|政策)`、`最近.{0,8}(进展|消息|新闻|动态|发布|出了|上线)`、`刚刚(发生|出|公布|上线)`、`今年.*(最新|发布|出了)`

> 踩坑记录 1：旧版有 `/现在.*(多少|几|什么)/`，导致「你现在都知道些关于我的什么信息」被判成要联网，去搜了一堆无关教程。修复方式就是要求两个词紧邻、不跨整句。
>
> 踩坑记录 2（2026-10-18）：「今天某市某区的天气是什么样的呢」**漏判**——旧正则 `(今天)(的)?(天气)` 要求紧邻，中间夹了"某市某区的"就断；「天气是什么样的」也不匹配 `(天气)(怎么样|如何|多少)`。现场表现为她回"我这儿看不到那边的天呢"，用户以为联网坏了。修复：时间词与话题间放宽到 14 字，并补 `什么样/咋样/冷不冷` 等口语句式。

### 3.2.1 查询词构造 `buildSearchQuery(text, sceneTopic)`

**不要把用户原话直接当 query。** 现场案例：用户回了句「你搜一下嘛」，代码把这三个字发给搜索接口 → 返回一堆无关网页 → 她只能说"没搜到"。

```js
// src/websearch.js
buildSearchQuery(text, sceneTopic)
// ① 剥口气词：^(你|帮我|请|麻烦|能不能|可不可以|可以)+ 与 搜一下|搜搜|搜索|搜|查一下|查查|查|百度一下|百度|谷歌|上网查 及尾缀 嘛|呀|呢|吧
// ② compact < 6 字，或匹配 HEADLESS（天气|气温|温度|几点|时间|价格|多少钱|多少度|新闻|情况|行情 + 什么样/怎么样/如何…）
//    → 用场景话题补主语；话题里已含同一个词则直接用话题，避免"今天的天气 天气怎么样"重复
```

实测：`你搜一下嘛` + 场景`今天某市某区的天气是什么样的呢` → `今天某市某区的天气是什么样的`；`帮我查一下显卡价格` → `显卡价格`。

另有 **手动** `/搜 <关键词>` 走同一个 `webSearch`。

### 3.3 结果如何注入回答

搜索结果**不直接发给用户**，而是拼成一段"参考资料"塞进本轮动态上下文：

```
【联网搜索到的真实资料】
搜索摘要（根据抓到的网页整理）：
<sr.answer，最多 1200 字>

来源：
1. <标题前 60 字>
   <snippet 前 100 字，空白归一>
   <url>
2. ...
（formatSources 最多 4 条）

请基于上面这些真实资料回答，把结果说成自己的话（不要罗列网址）。
如果资料里确实没有相关信息，就老实说没查到，绝对不要凭印象编造。
提到出处时说"网上查到的"就行。
```

**`answer` 必须注入（2026-10-18 修正）。** 原实现只注入 sources，而 DeepSeek 的 `web_search` 返回里 `snippet` 绝大多数为空（`citations[].cited_text` 只在模型自己产出带引用文本时才存在）。实测同一条 query：

| 注入内容 | 她的回答 |
|---|---|
| 只有 10 条 sources（标题+URL，snippet 全空） | "我搜啦，可是没搜到某区今天的天气 / 出来一堆乱七八糟的网页" |
| 加上 `answer` | "某区今天晴转多云，13~20℃，东北风 1~3 级，AQI 优~良" |

`answer` 是模型在 tool-use 循环里**真的读了网页**之后写的摘要（`webSearch` 已返回该字段，只是先前被丢弃），可靠性远高于标题。注意它仍是模型转述，摘要里若自带"各来源时间戳不一致"这类提醒，别当硬事实。
这段 `searchBlock` 与 `ragBlock`、条数要求一起 join 成 `dynamicContext`，由 `buildChatMessages` 放在 **messages[1]（第二条 system）**；DSH 模式下则进 `buildTask` 拼的提示词。`ok:false` 或 0 条结果时什么都不注入，只记日志。

## 4. dsh.js —— 备用/重量级通道（279 行）

### 4.1 什么时候用

- `--mode=dsh` 的主通道（每条消息都 spawn 一次，带全套工具，能真干活）；
- `/do <自然语言>` 匹配不到预设动作时回落 DSH（`src/index.js:933-940`，超时 `min(doTimeoutMs=120000, 180000)`）；
- chat 模式不做自动降级——`result.ok=false` 只把错误文案回给用户（"到底用哪个通道"是启动参数决定的，不是运行时 fallback）。

### 4.2 怎么调

`runTask(task, {timeoutMs=180_000, cwd=ROOT, profile='headless', signal})`：

```
spawn(process.execPath, [bin.js, '--profile', 'headless', task], {
  cwd, windowsHide: true,
  stdio: ['ignore', outFd, errFd],          // 不用管道
  env: {...process.env, NO_COLOR:'1', FORCE_COLOR:'0',
        DSH_HOME: WX_DSH_HOME || <ROOT>/data/dsh-home,
        DEEPSEEK_API_KEY: <key>}
})
```

- 命令解析 `resolveDshCommand()`：`DSH_BIN` 环境变量 → 本机 npx 缓存里的 `@deepseek-ai/dsh/lib/bin.js` → 退回 PATH 上的 `dsh`。
- **为什么不用 `stdio:'pipe'`**：受限环境下 Node 无法创建匿名管道，`spawn` 直接抛 `EPERM`；实测只有 `inherit / ignore / 文件描述符` 可行。这里用"把 stdout/stderr 各自绑到一个临时文件 fd"（`data/tmp/dsh-<ts>-<pid>-<rand>.out|.err`），既捕获输出又不碰管道。
- **stdout / stderr 必须分开**：headless 把最终答案写 stdout、思考过程写 stderr。早先合并成一个文件导致推理内容混进微信回复（出现 `dsh: reasoning: ...` 和大段英文思考）。现在 `text = stdout`，`reasoning = stderr` 只留诊断。
- 超时：`setTimeout(timeoutMs)` 到点 `SIGKILL` 子进程，返回 `超时 N 秒未完成`；也支持外部 `signal` 取消（返回"已取消"）。
- 退出码非 0：优先取 stderr（真正的报错），`slice(-700)` 附在错误里；同时把 `=== exit N === --- stderr --- --- stdout ---` 完整现场写到 `data/logs/failed-<ISO>.log`。
- 输出临时文件用完即删（成功失败都删）。

### 4.3 独立 HOME 的作用

`DSH_HOME` 默认**强制**指向项目内的 `data/dsh-home`，只有显式设 `WX_DSH_HOME` 才覆盖（`src/dsh.js:177-183`）：

- 受限环境（沙箱/杀软/只读配置）下 DSH 写不进 `~/.dsh/profiles`，表现为 `EPERM`；搬到项目内 → 桥完全自包含，换机器/换启动方式都不会因权限挂掉。
- **不能沿用继承来的 `DSH_HOME`**：桥本身可能就从某个 DSH 会话里启动，那个会话已把 `DSH_HOME` 设成 `~/.dsh`，沿用会绕回原来的权限问题。
- 代价：项目内 HOME 没有凭证库 → `readDshApiKey()` 先读环境变量，再读 `~/.dsh/.credentials.yaml` / `credentials.yaml`，把 key 通过 `DEEPSEEK_API_KEY` 环境变量喂给子进程。副作用：`data/dsh-home/` 下会出现 `sessions/`、`storages/session_projcache/`、`profiles/headless/` 等运行痕迹。

## 5. launch.js —— 进程守护（132 行）

### 5.1 存在理由

以前重启桥用 `Stop-Process node -Force`，把 DSH Web（3080）一起杀了。启动器把自己 fork 的子进程 PID 写进 `data/bridge.pid`，之后**只按这个 PID 精确停止**，绝不波及其它 node 进程。

### 5.2 文件与重定向

| 项 | 值 |
|---|---|
| PID 文件 | `data/bridge.pid`（纯文本十进制 PID） |
| stdout 日志 | `data/run.log`（`openSync(..., 'w')`，**每次启动覆盖**） |
| stderr 日志 | `data/tmp/stderr.log`（同样覆盖写，目录先 `mkdirSync(recursive)`） |
| 子进程 | `node src/index.js --mode=<mode> <其余参数>`，`detached: true` + `child.unref()`，`cwd = 项目根`，`stdio: ['ignore', outFd, errFd]`（同样规避管道 EPERM） |

### 5.3 命令行

| 参数 | 行为 |
|---|---|
| `node launch.js --mode=chat`（默认） | 后台启动；若 PID 记录仍存活则只提示"已在运行，如需重启请用 --restart" |
| `node launch.js --stop` | 读 PID → `SIGTERM` → **忙等最多 5000 ms**（每 100 ms 自旋）→ 仍存活则 `SIGKILL` → 删 PID 文件。无记录/进程已死都返回 0 并顺手清理 |
| `node launch.js --status` | 打印"运行中 PID=…"或"未运行/已退出（记录已过期）"，并回显 `data/run.log` 最后一行非空日志；**未运行返回退出码 1** |
| `node launch.js --restart [--mode=…]` | `stop()` 后 `start()` |
| 其它参数 | 原样透传给 `src/index.js`（会剔除 `--mode=*`、`--restart`、`--stop`、`--status`） |

### 5.4 崩溃重启策略

**没有自动重启**：`launch.js` 只做"启动 + 精确定位 PID + 停止 + 状态"，不监控子进程、不拉起、不写心跳。子进程崩溃后 `data/bridge.pid` 会残留，`--status` 收敛为"已退出（PID 不存在，记录已过期）"。要自愈得外挂（计划任务 / supervisor），且注意 `run.log` 每次启动被覆盖——历史日志需自己转存。

## 7. 写教程时的 6 个"坑位清单"

1. `iLink-App-Id: bot` + `iLink-App-ClientVersion: 132106` 必须每条请求都带；只差这两个头，文字能通、媒体会显示"已清理/已过期"。
2. 二维码不是图片，是把 `qrcode_img_content` 这条链接打印出来、用手机微信打开。
3. `context_token` 是硬门槛：没有它一条消息都发不出去，所以"主动消息"没有官方保证（`cfg.proactive` 默认 false）。
4. `aes_key = base64(hex 字符串)`，不是 `base64(原始 16 字节)`。
5. chat 模式的 system 必须拆成"稳定人设 + 每轮动态上下文"两段，否则前缀缓存恒为 0，每条消息全价重付人设。
6. `stdio` 不要用 `'pipe'`（受限环境 EPERM）；stdout 是答案、stderr 是推理，合并会把思考过程发到微信里。

## 8. scene.js —— 场景延续与分层知识注入（2026-10 新增，约 345 行）

### 8.1 解决的问题

2026-10 之前每条回复的上下文只有：人设（固定 system）+ 近 3 轮原文 + 当轮动态上下文。
缺"我们正在聊哪件事"这一层，导致三个具体症状：

- 用户说"那显卡呢"，模型不知道"那"指哪张卡；
- 主动消息每次 `pickScenario()` 重抽，上一分钟聊桂花、下一分钟问"忙不忙"；
- 一个话题聊到第 5 轮，模型想不起第 2 轮的前提。

根因：**场景从来没被存成状态**，每轮从零拼上下文。

### 8.2 数据结构

```js
{
  topic, keywords[], startedAt, updatedAt, turns,
  progress[],        // 最近 MAX_PROGRESS=4 条，每条 clip 到 MAX_TEXT=120 字
  lastUserText, lastReplyText, openQuestion,
  lastNewTopicAt, lastNewTopicSource
}
```

落盘 `data/scenes/<encodeURIComponent(userId)>.json`，内存 `Map` 缓存（`cache`），一人一文件。

### 8.3 导出函数（主要 11 个；另有 loadScene / saveScene / resetScene 管读写）

| 函数 | 说明 |
|---|---|
| `keywordsOf(text, limit=18)` | 中文 bigram + 英文/数字串；过停用词 `STOP` |
| `topicOf(text)` | 一句话话题（截断/去噪） |
| `createScene(userText, opts)` | 新场景；保留旧场景的 `lastNewTopicAt` |
| `analyzeTurn(userText, scene, opts)` | 本地判定 `new / continue / ambiguous` |
| `recordUserTurn(scene, text)` | turns++ + lastUserText |
| `recordReply(scene, replyText)` | progress.push，抓 openQuestion |
| `lastQuestionOf(text)` | 从句末抽"问过但没答"的那句 |
| `canOpenNewTopic(scene, {intervalMs})` | 冷却判定 |
| `markNewTopic(scene, userText, opts)` | 换题 + 落锚点 |
| `formatSceneForReply` / `formatSceneForProactive` | 生成注入段落 |

### 8.4 analyzeTurn 判定顺序（本地优先）

```
1. scene 为空/过期(sceneTtlMinutes)      → new
2. ACK_RE（嗯/哦/好/哈哈/在呢…）          → continue（score 0.5）
3. REF_RE（后来/那个/接着/刚才/它…）      → continue
4. score >= 0.18                          → continue
5. text.length <= 6                       → continue
6. score <= 0.08                          → new（用户自己换题）
7. 其余                                    → ambiguous（交给上层）
```

`score = |交集(keywordsOf(text), scene.keywords)| / |keywordsOf(text)|`。

### 8.5 index.js 侧接线

- 回复路径（`handleWithDsh`）：`analyzeTurn` → `new` 则 `createScene`，`continue` 则 `recordUserTurn`；`ambiguous` 在 `sceneAnalyzeModel='auto'` 且未超 `sceneAnalyzeMaxPerHour`（默认 6/小时，滑动 1 小时窗口，模块级数组 `sceneJudgeTimes`）时调模型判 `CONTINUE`/`NEW`，否则一律 continue。
- 生成后：成功/失败两条分支都 `recordReply` + `saveScene`。
- 主动路径（`composeProactive`）：`allowNewTopic = !scene || canOpenNewTopic(...) || scene.turns >= sceneMaxTurns`；再掷 85% 概率 `wantNewTopic`；`continueMode = !escalate && !wantNewTopic && !!prevLine`。
- 兜底句/新话题都 `markNewTopic` 并落盘；升级档（`escalate`）不换题。

### 8.6 分层知识注入

| 层 | 来源 | 每轮 | 触发 |
|---|---|---|---|
| 1 | `getProfileDigest(vaultPath, profileNotes, sceneProfileChars=360)` | 是 | `sceneProfileChars > 0` |
| 2 | `searchVault(text, {topK: 3, minScore: 0.35})` | 是 | `ragEnabled` |
| 3 | 自指句：画像加厚到 `profileMaxChars`(1200) + topK→2 | 按需 | `isSelfReferential(text)` |

注入点：`dynamicContext`（chat 的 messages[1]），不碰人设那条 system，保前缀缓存。

### 8.7 配置项

### 8.8 教训

- **两台闸门别混**：用户换题无条件放行；AI 换题才受 `proactiveNewTopicMinutes` 约束。
- **`markNewTopic(null, …)` 每次传 null 会让冷却锚点永远刷新** → 表现为从不允许开新话题。

### 8.9 近期话题层（2026-10-18 新增）

`vault.js` 新增两个导出：

- `getRecentTopics(vaultPath, { days = 30, maxItems = 5 })` → `[{ rel, title, mtimeMs }]`，按 mtime 倒序。
  排除三类噪声（常量在 vault.js 顶部）：`GENERATED_DIRS = ['00-第二大脑','session-log','brain-collector']`（采集管道每跑一次都重写，mtime 恒为"刚刚"）、`NOT_A_TOPIC = /^(MOC|INDEX|README)$/i`、`ARCHIVE_SEGMENTS = ['对话档案']`。

### 8.11 发送窗口实测：约 10 分钟，不是 30 分钟（2026-10-18）

`proactive.js` 里 `contextTtlMs` 默认 30 分钟，是按官方说法设计的。但 2026-10-18 19:00 前后实测发现真实窗口短得多：用户 18:52:46 说完最后一句，18:58:03 还能 4/4 发送成功，19:00:38 只成功 1/5，19:02:09 全失败（`errmsg: "prepare failed"` = `ret=-2`），随后 `closeWindow()`。

结论与对策：
- 窗口 ≈ 最后一条用户消息 + 10 分钟。`proactiveContextTtlMinutes` 应设 10，设 30 只会在窗口关闭后继续白撞请求。
- 节奏不能设成 1-3 分钟：10 分钟窗口内能发十几条，把 `silentStreak` 顶到 `burstAfter`，触发升级连发，观感像刷屏，然后彻底安静。
- 采用窗口友好配置：`proactiveMinMinutes=5`、`proactiveMaxMinutes=12`、`proactiveIdleMinutes=3`、`proactiveContextTtlMinutes=10`、`proactiveBurstAfterIdleMinutes=8`、`proactiveBurstAfter=2`、`proactiveBurstMinCount=2`、`proactiveBurstMaxCount=3`。
- 重启进程会丢掉 `lastUserSpokeAt`（只在内存），**重启后必须等用户先说一句话，主动消息才会重新开始**。这是"重启后不主动发消息"的最常见原因。
